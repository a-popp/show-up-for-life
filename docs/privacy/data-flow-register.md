# Data-flow register

This register is a planning artifact for the future application. It should be updated before implementation and reviewed whenever data collection, visibility, retention, or processors change. Treat availability, location, relationship, safety, and behavioral follow-through data as sensitive even when not legally classified as special-category data.

| Data flow | Purpose | Data elements | Sensitivity | Visibility | Retention | Export/delete behavior | Notes |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Account/profile | Authentication, identity, user control | Email, name/display name, auth identifiers, profile preferences | Moderate | User-controlled; minimum necessary | Until account deletion plus limited legal/security backup window | Export and delete through user controls | No public profile by default unless required and visible |
| Events/RSVPs | Host planning and attendance | Event details, invitations, responses, cutoffs, waitlist state | Moderate to high | Host/attendee visibility as designed; no unnecessary public visibility | Event lifecycle plus defined archive window | Include in export; deletion subject to aggregate/non-identifying needs | Cancellation copy must not shame users |
| Availability | Matching hosts with willing attendees | Scheduled/spontaneous windows, expiry, per-type visibility settings | High | Opt-in, relationship-based; hosts see only event-specific availability | Expire spontaneous data automatically; retain only as needed | Export/delete with account controls | Never an RSVP or commitment |
| Location/proximity | Distance and preference matching | Postal code/city, optional exact address, coarse derived distance, travel preferences | High | Never expose postal code/city/exact address to hosts/other users | Keep only current preference data; derived values as needed | Export/delete with account controls | No real-time/device location in initial release |
| Relationships/groups | Visibility, eligibility, community membership | Friendship/group links, invitations, membership roles | High | Visible only as needed to participants | Until removed/account deletion; audit minimum necessary | Export/delete with account controls | Friendship mutuality is open decision OD-2 |
| Moderation/reports | Trust and safety workflows | Reports, reporter/reported user, evidence, status, actions | High | Restricted to authorized reviewers | Defined retention based on safety/legal need | Handle carefully; safety records may need limited exceptions | Protect reporter privacy and anti-retaliation |
| Notifications | Reminders and transactional messaging | Recipient, event type, preferences, delivery status, unsubscribe/preferences | Moderate | User-controlled preferences | Delivery logs minimum necessary | Preference deletion/export where feasible | No open/click tracking by default |
| Analytics/measurement | Product outcomes and service health | Aggregated events, timestamps, coarse metadata | Moderate | Internal only; avoid user-level surveillance | Prefer aggregation/short retention | Honor deletion where reasonably possible | No sensitive inferences or dark-pattern optimization |
| Email processing | Transactional delivery | Email address, message metadata, template variables, provider status | Moderate | User and authorized operators only | Provider retention plus minimal local logs | Delete/export with account data where feasible | Mailgun processor; document subprocessors before launch |

Open questions must be resolved before implementation rather than during incident response.
